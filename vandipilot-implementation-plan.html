Fig. 00 — Open Items

Decisions needed before build

Three items block or reshape Phase 1, plus three open product questions that affect the booking flow and driver-profile schema.

⬤ Brand refresh

A completely new color scheme and design language has been requested. 2–3 mockup options are needed for the client to pick a direction (warm vs. cool tones, light vs. dark primary theme) before UI build begins.

⬤ Supabase project

Requires a Supabase project URL + anon key, plus a Google OAuth client ID/secret configured in Supabase Auth settings.

▲ Admin email (hardcoded)

The admin role is resolved by matching a hardcoded Gmail address. Confirmation of which account is required before the auth middleware can be finalized.

  • Driver background-check criteriaWhich checks are actually performed (Aadhaar verification, police clearance, driving test, reference calls)? Displayed on the landing page and stored on the driver profile.
  • Booking time granularity30-minute slots, 1-hour slots, or a free-form time picker?
  • Multi-stop tripsDoes a trip support multiple stops (Pickup → Hospital → Pharmacy → Home), or is it always a single destination with round-trip?

Fig. 05 — Surfaces

Customer · Driver · Admin

Each role gets a dedicated dashboard and a small set of task-specific pages.

Customer

Book, track, rate

  • /customerWelcome banner, "Book a Pilot" CTA, active/upcoming trips, trip history, services & pricing cards, notification bell
  • /customer/bookPre-filled car type/transmission, pickup, destination, date & time picker → creates a requested booking, notifies admin. Round-trip by default
  • /customer/trips/[id]Status timeline; driver name/phone/photo once assigned; fare breakdown + 1–5 star rating after completion
  • /customer/profileEdit name, phone, default pickup address, default vehicle. Email & photo read-only from Google
Driver / Pilot

Run trips, get paid

  • /driverUpcoming trips, active-trip card with contextual status buttons, quick stats, notifications, calendar link
  • /driver/trips/[id]Full trip detail; large next-action button only (Start Running → Arrived → Left → Complete); fare + commission shown after completion, "Mark Commission Paid"
  • /driver/earningsPer-trip breakdown (running/waiting/fare/commission/net), weekly/monthly toggle, commission status
  • /driver/calendarAssigned trips by date; mark days off; visual booked/available/off indicators
Admin

Dispatch & oversee

  • /adminKPI cards (bookings, active trips, drivers, customers, revenue, pending commissions), recent bookings, alerts
  • /admin/bookings(/new)Filterable table; assign driver (filtered by availability + vehicle match); cancel with reason; manual booking incl. inline new-customer creation
  • /admin/drivers(/new)Driver table w/ status, trips, rating; add/edit; deactivate/ban toggle
  • /admin/customersCustomer table, booking history, ban/unban
  • /admin/commissionsPending / Driver Marked Paid / Admin Confirmed, filterable, "Confirm Payment"
  • /admin/reportsRevenue summary, per-driver report, trend charts
  • /admin/pricingEditable rate tiers feeding the landing page & fare engine
  • /admin/ratingsAll ratings, filter by driver/level

Fig. 08 — QA

Verification plan

Automated tests

  • RLS policies — customers see only their bookings; drivers see only assigned trips; admin sees everything
  • Fare calculation unit tests against sample timestamps
  • Auth flow integration tests — Google sign-in → role routing

Manual verification

  • End-to-end: customer books → admin assigns driver → status transitions → fare calculated → rating submitted
  • Commission flow: driver marks paid → admin confirms
  • Admin manually creates a customer + booking
  • Driver sets days off → excluded from availability
  • Responsive testing on mobile browsers — primary use case for drivers
